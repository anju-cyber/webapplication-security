Broken Access Control (BAC) — Web Pentesting Notes
One of the MOST IMPORTANT vulnerabilities in web security.
From OWASP, Broken Access Control has remained one of the top risks because it often leads directly to:
•	Account takeover 
•	Admin access 
•	Sensitive data exposure 
•	Full application compromise 
________________________________________
1. What is Access Control?
Access Control decides:
WHO can access WHAT
and
WHAT actions they are allowed to perform
________________________________________
Simple Example
Normal user:
- View own profile
- Edit own data

Admin:
- Manage all users
- Delete accounts
- Access admin panel
________________________________________
2. What is Broken Access Control?
Broken Access Control happens when application fails to properly enforce permissions.
Result:
User can:
•	access unauthorized data 
•	perform unauthorized actions 
•	become admin 
•	bypass restrictions 
________________________________________
Simple Definition
Application trusts user too much.
________________________________________
3. Authentication vs Authorization
VERY IMPORTANT.
________________________________________
Authentication	Authorization
Who are you?	What can you access?
Login process	Permission checks
Example: password	Example: admin access
________________________________________
Example
Login successful = Authentication
But:
Can user access /admin? = Authorization
________________________________________
4. Access Control Models
________________________________________
A. Role-Based Access Control (RBAC)
Permissions based on roles.
________________________________________
Example
Role	Permissions
User	View own profile
Moderator	Manage posts
Admin	Full control
________________________________________
B. Attribute-Based Access Control (ABAC)
Access depends on:
•	user attributes 
•	environment 
•	conditions 
________________________________________
Example
Employee can access payroll only during office hours.
________________________________________
C. Discretionary Access Control (DAC)
Owner controls permissions.
________________________________________
Example
Google Drive sharing.
________________________________________
D. Mandatory Access Control (MAC)
Strict centralized control.
Used in:
•	military 
•	government systems 
________________________________________

6. Vertical Privilege Escalation
User becomes higher privileged user.
________________________________________
Example
Normal user accesses:
/admin
and gets admin panel.
________________________________________
Example Flow
User account
     ↓
Access admin endpoint
     ↓
Admin access gained
________________________________________
Causes
•	missing backend checks 
•	frontend-only restrictions 
•	hidden admin URLs 
________________________________________
Risks
CRITICAL.
Can lead to:
•	full system compromise 
•	deleting users 
•	viewing all data 
________________________________________
Mitigation
Always validate roles server-side.
________________________________________
7. Horizontal Privilege Escalation
User accesses another user's data.
________________________________________
Example
GET /profile?id=1001
Change to:
GET /profile?id=1002
________________________________________
Result
Access another user's account.
________________________________________
Risks
Sensitive data exposure.
________________________________________
Mitigation
Verify ownership server-side.
________________________________________
8. IDOR (Insecure Direct Object Reference)
MOST IMPORTANT BAC vulnerability.
________________________________________
Concept
Application exposes internal object references directly.
Example:
•	user IDs 
•	file IDs 
•	order IDs 
without proper authorization checks.
________________________________________
Example
GET /invoice/1001
Change to:
GET /invoice/1002
and access another invoice.
________________________________________
Why Dangerous?
Easy to exploit.
Often exposes:
•	PII 
•	financial data 
•	medical records 
•	internal documents 
________________________________________
Types of IDOR
________________________________________
A. Numeric IDOR
?id=1
?id=2
________________________________________
B. UUID IDOR
?id=6f8a-123a-abc
Still vulnerable if auth missing.
________________________________________
C. File IDOR
/download?file=invoice.pdf
________________________________________
D. API IDOR
GET /api/user/1002
________________________________________
Mitigation
Never trust object IDs alone.
Always verify:
Does this user own this object?
________________________________________
9. Forced Browsing
Accessing hidden/restricted pages directly.
________________________________________
Example
/admin
/debug
/internal
________________________________________
Risks
Hidden functionality exposed.
________________________________________
Mitigation
Do not rely on hidden URLs.
Enforce backend authorization.
________________________________________
10. Missing Access Control
Application forgets permission checks.
________________________________________
Example
Delete endpoint:
POST /deleteUser
No authorization validation.
________________________________________
Risks
Anyone can perform sensitive actions.
________________________________________
Mitigation
Protect every sensitive endpoint.
________________________________________
11. Client-Side Access Control
Frontend controls permissions.
VERY common beginner mistake.
________________________________________
Example
JavaScript hides admin button:
if(role=="admin")
But backend never validates.
________________________________________
Risks
Attacker bypasses frontend easily.
________________________________________
Mitigation
Authorization MUST happen server-side.
________________________________________
12. Parameter-Based Access Control
Application trusts user-controlled parameters.
________________________________________
Example
{
  "role":"user"
}
Changed to:
{
  "role":"admin"
}
________________________________________
Risks
Privilege escalation.
________________________________________
Mitigation
Never trust client-supplied roles.
________________________________________
13. API Authorization Flaws
EXTREMELY common today.
________________________________________
Example
GET /api/admin/users
API lacks authorization checks.
________________________________________
Risks
Massive data exposure.
________________________________________
Important API Access Control Types
Type	Meaning
Object-Level	Access to object
Function-Level	Access to functionality
Property-Level	Access to fields
________________________________________
14. Broken Object-Level Authorization (BOLA)
API version of IDOR.
VERY important.
________________________________________
Example
GET /api/orders/1001
Change:
GET /api/orders/1002
________________________________________
Risks
One of most common API vulnerabilities.
________________________________________
15. Function-Level Authorization
User accesses unauthorized function.
________________________________________
Example
POST /api/admin/delete-user
Normal user can access it.
________________________________________
Risks
Admin action abuse.
________________________________________
16. Method-Based Access Control Bypass
Different HTTP methods behave differently.
________________________________________
Example
GET /admin → blocked
POST /admin → allowed
________________________________________
Risks
Method tampering bypass.
________________________________________
Mitigation
Validate ALL methods.
________________________________________
17. Multi-Step Process Bypass
Application validates only some steps.
________________________________________
Example
Step1 → Auth
Step2 → Payment
Step3 → Download
Attacker directly accesses:
Step3
________________________________________
Risks
Workflow bypass.
________________________________________
Mitigation
Validate authorization at every step.
________________________________________
18. JWT Role Manipulation
JWT contains user role.
________________________________________
Example
{
  "role":"user"
}
Changed to:
{
  "role":"admin"
}
If signature validation weak:
•	privilege escalation possible 
________________________________________
Mitigation
Proper JWT validation.
________________________________________

23. Broken Access Control Testing Methodology
VERY IMPORTANT.
________________________________________
Step 1 — Map Roles
Identify:
•	guest 
•	user 
•	admin 
•	moderator 
________________________________________
Step 2 — Compare Requests
Use:
•	Burp Suite Repeater 
•	Comparer 
Observe differences.
________________________________________
Step 3 — Test IDOR
Change:
•	IDs 
•	UUIDs 
•	filenames 
•	object references 
________________________________________
Step 4 — Test Role Escalation
Modify:
•	role parameters 
•	JWT claims 
•	cookies 
________________________________________
Step 5 — Test Hidden Endpoints
Try:
/admin
/internal
/manage
/api/admin
________________________________________
Step 6 — Test HTTP Methods
Try:
•	GET 
•	POST 
•	PUT 
•	PATCH 
•	DELETE 
________________________________________
Step 7 — Test APIs
Focus heavily on:
•	object ownership 
•	admin APIs 
•	mobile APIs 
________________________________________
24. Pentester Mindset
Never think:
"User is logged in, so access is okay."
Think:
"Should THIS user access THIS resource THIS way?"
That is the core of authorization testing.
